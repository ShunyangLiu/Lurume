# 大模型翻译耗时排查（2026-09-09）

测试源码基线：v0.0.11（a6eb4a8）。本次仅增加耗时测试，没有修改翻译行为或发布新版本。

## 已测范围

通过真实 TranslationController → TranslationXPCClient → 嵌入的 Translation XPC → 本地 HTTP 固定响应 → 主线程 published 状态，测试 20 次。每组 5 次。空凭据存储替身、不访问用户论文、无模型计费。首段“显示”计时终点是 translatedText 发布，不是屏幕实际绘制。

双翻译组启动了两种请求，但未驱动 Apple 的真实翻译执行，因此仅代表双翻译编排开销，不代表系统引擎满负载时的竞争。Debug 构建、单台开发机、小样本，不能作为所有设备的保证。

| 模式 | 请求准备中位数 | XPC + 本地 HTTP 首段中位数 | 主线程发布中位数 | 首段总耗时中位数 | 首段总耗时范围 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 手动模型翻译 | 0.10 ms | 2.70 ms | 0.02 ms | 2.79 ms | 2.34–112.83 ms |
| 自动模型翻译 | 251.81 ms | 12.02 ms | 0.08 ms | 263.62 ms | 258.89–270.16 ms |
| 双翻译编排，手动 | 0.80 ms | 11.47 ms | 0.07 ms | 12.23 ms | 8.81–13.25 ms |
| 双翻译编排，自动 | 252.23 ms | 9.01 ms | 0.07 ms | 261.31 ms | 258.33–266.93 ms |

第一条手动请求含冷启动，首段耗时 112.83 ms。后续请求的进程、网络栈可能受前序请求预热影响；不能把组间差异解读为稳定的模式性能差异。

## 源码确认的设计开销

- 自动划词去抖等待 250 ms，避免拖动选区时连续发起请求。
- 第一段模型正文立即发布；后续增量最多合并等待 40 ms。
- 每次完成后关闭空闲 XPC 连接；每次请求新建 ephemeral URLSession，缺少跨请求的连接复用。存在优化空间，但本地测试不能量化真实 HTTPS 上的收益。
- 模型请求不等待系统翻译结束；本地编排不存在串行等待系统译文的设计。

## 当前豆包配置与未证实项

用户确认当前使用 doubao-seed-2.0-mini，地址为火山 Coding 接口 /api/coding/v3。本机保留配置中服务商字段缺失，按 custom 处理，流式开启。

目前 disablesThinking 仅对指定服务商预设或 Anthropic 协议生效，自定义火山地址不会发送 thinking.type=disabled。若后端先生成思考内容，正文首段会延后，这是待验证的嫌疑点，尚未通过真实模型响应确认。

未找到当前本地凭据文件；定向读取旧翻译钥匙串项未成功，因此没有进行带 Key 的模型调用，也没有测到排队、思考或生成耗时。

对同一接口的三次不带凭据连通性探测返回 401，总耗时 270、51、62 ms（curl 当前网络路径）。这仅说明请求可到达认证入口，不代表模型推理耗时，也不能等同于 App 的 URLSession 建连耗时。

## 结论与下一步

已证实的软件本地开销约为自动划词 0.25 秒、冷启动约 0.11 秒，首段发布本身低于 0.1 ms。当前数据不能将数秒等待归因于本地文字处理或主线程分发；也不足以证明服务端就是唯一瓶颈。

下一步需可用的当前服务凭据，以固定短句和段落分别测：HTTP 建连、首个 SSE、首个正文、完成时间，并在服务支持时对比关闭思考参数。保留原地址与模型，不自动切换到按量计费接口。

复跑入口：Tests/P7Translation/run-xpc-integration-tests.zsh；测试用例 TranslationXPCIntegrationTests.testTranslationLatencyBreakdown。若需要打印每次结果，移除 xcodebuild 的 -quiet，查找 TRANSLATION_LATENCY_JSON。

## 后续连接复用实现与验证

v0.0.12 改为同一客户端连续复用 XPC（空闲 30 秒释放），同一服务连接复用禁用 Cookie、缓存和凭据存储的 URLSession。每个请求仍独立持有请求头、计时器和取消状态。完成的响应允许最多 2 秒排空以便 TCP 连接复用。

新增测试确认连续四次流式／非流式请求复用同一个服务端观察到的客户端端口，Key 的更换和移除正确生效；取消一个并发请求不影响另一个；超时及跨源重定向失败后仍可继续请求。

复用单个客户端重测 20 次，首段发布中位数：手动模型 5.93 ms、自动模型 256.44 ms、双翻译编排手动 4.27 ms、双翻译编排自动 256.66 ms。自动组 XPC + 本地 HTTP 首段约 4.6–5.0 ms。测试环境与样本限制同上；没有进行真实豆包生成速度的前后对比，不宣称秒级优化。
