# Lurume P6 应用内更新与发布基础设施计划

状态：检查点一已实现并通过隔离更新验证，等待验收后进入检查点二
更新日期：2026-08-29

## P6 目标

P6 为 GitHub 独立分发的 Lurume 增加一条安全、可重复、对阅读流程低干扰的应用内更新链路。用户手动安装首个包含 Sparkle 的引导版本后，可以由应用定期检查稳定版本、查看中文更新说明，并在明确确认后完成下载、安装和重启。

```text
开发者在本机准备版本
→ 测试、构建并生成 DMG
→ 使用 EdDSA 签名 DMG、appcast 与更新说明
→ 明确确认后发布 GitHub Release
→ 下载地址验证通过后更新 GitHub Pages
→ Lurume 定期检查并提示用户安装
```

P6 第一版只完成“Sparkle 标准更新界面 + 单一稳定通道 + 本地两阶段发布脚本 + 完整签名验证”的纵向链路，不同时扩展文献阅读或管理功能。

## 已确认的产品边界

- 使用 Sparkle 2 作为应用内更新框架。它是当前唯一允许的运行时第三方依赖，也是 macOS 系统框架无法提供等价能力的发布基础设施例外。
- P6 不加入 Apple Developer Program，不实现 Developer ID 签名或苹果公证；首次安装仍沿用 README 中的手动放行流程。
- 用户必须手动安装首个包含 Sparkle 的 `v0.0.3`；从 `v0.0.4` 开始验证完整的应用内升级。
- 只提供一个稳定更新通道，不提供 Beta、Nightly、预发布订阅或强制升级。
- 首次启动不显示更新权限提示；第二次启动使用 Sparkle 标准界面询问是否允许自动检查。
- 用户允许后默认每 24 小时后台检查一次；检查到新版本时提示，不静默下载、安装或重启。
- 应用菜单始终提供“检查更新…”，设置窗口的“通用”页提供“自动检查更新”开关。
- 更新界面使用 Sparkle 标准用户界面，不为 P6 自制更新窗口、进度界面或发布说明浏览器。
- appcast 托管在 Lurume 的 GitHub Pages，更新包继续使用 GitHub Release 中的 DMG。
- P6 不把更新私钥交给 GitHub Actions、GitHub Secrets 或其他云端服务；构建、签名和 appcast 生成都在开发者本机完成。
- DMG 不再被要求必须小于 10 MB，但 P6 必须测量并记录包体、启动耗时和运行时内存变化。

## 与轻量化承诺的关系

README 已由后续产品裁决调整：不再以“安装包保持个位数 MB”作为硬门槛，而是要求体积和运行时持续保持轻量。P6 按以下规则执行：

- Sparkle 之外不新增第二个运行时第三方依赖；发布脚本优先使用 macOS、Xcode、Sparkle 和 GitHub CLI 已有工具。
- 不为了缩小包体使用旧版 Sparkle、移除签名验证、删除沙盒安装服务或降低更新安全性。
- 更新检查不得同步阻塞应用启动、PDF 打开、翻译、高亮、笔记保存或文献库操作。
- 不安装常驻 LaunchAgent、LaunchDaemon 或自建后台服务；Sparkle 的辅助进程只在检查、下载或安装期间运行。
- 每次发布记录 App 与 DMG 体积；每个 P6 验收版本记录冷启动、稳定空闲内存和更新检查后的内存回落情况。
- 连续多次“无更新”检查不得造成主进程内存持续增长；检查结束或更新窗口关闭后不得长期残留更新辅助进程。

## 依赖与版本策略

- 通过 Swift Package Manager 引入 Sparkle 官方仓库 `https://github.com/sparkle-project/Sparkle`。
- 实现开始前重新核对官方最新稳定版和安全公告；本计划自审时的基线为包含最新安装安全修复的 Sparkle `2.9.6`。
- 工程必须固定一个经过验证的确切版本，不采用自动漂移到未来小版本的依赖范围。
- 升级 Sparkle 本身需要单独查看变更记录、重新运行沙盒更新测试并记录 App、DMG 和内存变化。
- `Package.resolved` 与工程声明一起纳入版本控制，保证发布构建可复现。
- 不复制或修改 Sparkle 源码，不私有分叉；如果必须修改上游核心组件，先停止并取得用户确认。

## 用户更新体验

### 自动检查许可

- 首次启动保持安静，不显示更新相关弹窗。
- 第二次启动由 Sparkle 标准权限界面询问是否允许自动检查更新。
- 用户拒绝后不自动检查，但仍可随时使用“检查更新…”。
- 设置中的“自动检查更新”直接绑定 Sparkle 自己的更新偏好，不在 `AppSettings` 中再保存一份容易失配的副本。
- P6 不发送系统配置档案、文献数据、文件路径、PDF 内容、高亮、笔记或翻译内容。
- 自动检查会向 GitHub Pages 暴露正常 HTTPS 请求所必需的网络信息以及应用版本；除此之外不加入遥测、统计或设备画像。

### 手动检查

- Lurume 应用菜单增加“检查更新…”，使用 Sparkle 的 `canCheckForUpdates` 状态决定是否可用。
- 没有新版本时使用 Sparkle 标准结果，不自制第二套提示。
- 手动检查失败时显示可理解的中文错误；网络失败、更新源暂时不可达或 GitHub 限流不影响其他功能。
- 后台自动检查失败时保持低干扰，不在每次启动反复弹出错误。

### 发现与安装更新

- 更新窗口显示 Lurume 名称、当前版本、目标版本和中文更新说明。
- 保留 Sparkle 标准的“安装”“稍后提醒”和“跳过此版本”等行为，不增加自定义强制倒计时。
- 第一版明确关闭静默自动下载和自动安装；必须由用户确认后才下载安装。
- 安装重启前必须让现有页面位置、文献库延迟保存和正在编辑的笔记通过现有退出边界完成持久化。
- 更新完成后恢复现有文献库、当前论文和阅读位置；P6 不修改文献库或高亮 schema。
- 从只读 DMG、不可写位置或受 App Translocation 影响而无法更新时，手动检查应给出“先把 Lurume 移入应用程序文件夹”的准确引导；后台检查不持续打扰。

## 更新架构

### 应用内组件

- SwiftUI 应用生命周期中持有一个 `SPUStandardUpdaterController`，使用 Sparkle 标准用户驱动更新主 App bundle。
- 更新控制器生命周期与应用一致，但不得在主线程同步执行网络请求或更新包处理。
- 应用菜单与设置只通过一个轻量封装读取和修改 Sparkle 状态，不复制更新调度器。
- P6 不把更新逻辑塞入 `ContentView`、`LibraryStore`、`TranslationController`、`HighlightStore` 或 PDF 阅读控制器。
- 为自动化测试提供最小协议边界，测试菜单可用性和设置绑定时不访问真实网络。

### App Sandbox

Lurume 主进程继续不申请通用 `com.apple.security.network.client` 权限。P6 使用 Sparkle 为沙盒应用提供的专用服务：

- 在 Info.plist 启用 Installer Launcher Service，允许 Sparkle 通过专用 XPC 安装更新。
- 在 Info.plist 启用 Downloader Service，由更新组件获取 appcast、更新说明和 DMG。
- 在 entitlements 中加入 Sparkle Installer 通信所需的两个基于 `$(PRODUCT_BUNDLE_IDENTIFIER)` 的 Mach lookup 临时例外。
- 保留现有 App Sandbox 与用户所选文件只读权限，不为更新扩大 PDF、文件系统或其他数据访问范围。
- 发布脚本不得使用 `codesign --deep` 进行重新签名；必须保持 Sparkle 内嵌 Framework、Updater 和 XPC 服务的签名及 entitlement 结构。

Sparkle 官方说明其预构建 Downloader XPC 在当前版本中默认不再自行沙盒化。P6 接受官方分发结构，但只允许该组件承担更新网络访问；如果实际审计发现它引入超出更新所需的持久权限、常驻进程或无法解释的访问，必须停止并重新评估，不能改为给整个 Lurume 静默增加网络权限。

### Info.plist 与更新源

P6 至少配置并验证以下 Sparkle 项：

- `SUFeedURL`：Lurume GitHub Pages 下固定的 HTTPS appcast 地址；
- `SUPublicEDKey`：与本地更新私钥对应的 EdDSA 公钥；
- `SUEnableInstallerLauncherService`：沙盒安装服务；
- `SUEnableDownloaderService`：专用下载服务；
- `SUVerifyUpdateBeforeExtraction`：解压前验证更新；
- `SURequireSignedFeed`：验证 appcast 和外部更新说明签名；
- `SUSignedFeedFailureExpirationInterval = 0`：禁用签名 feed 失败的时间到期回退，没有 Developer ID 时不允许绕过 feed 信任根；
- `SUAllowsAutomaticUpdates = NO`：不向用户提供后台下载或静默安装的选项，每次安装都需要明确确认；
- `SUEnableSystemProfiling = NO`：明确禁用匿名系统配置档案；
- `SUScheduledCheckInterval = 86400`：自动检查间隔为 24 小时。

不设置 `SUEnableAutomaticChecks`，保留第二次启动的许可询问；也不启用自动下载、自动安装或系统配置档案上报。实现时以所固定 Sparkle 版本的官方键名和行为为准，禁止凭旧版示例猜测配置。

## 更新签名与私钥

- 使用 Sparkle `generate_keys` 在开发者本机生成一对 EdDSA 密钥；公钥写入应用配置，私钥留在登录钥匙串。
- 额外导出一份私钥备份并放入由用户选择的加密离线存储；备份文件不得进入仓库、同步盘、构建产物、终端日志或 Codex 输出。
- P6 第一版的本地脚本默认从钥匙串读取私钥，不要求把私钥路径写入配置文件或命令行历史。
- DMG、appcast 和外部更新说明都使用同一受控密钥体系签名；发布前逐项验证签名。
- 因为没有 Developer ID，EdDSA 私钥是现有安装唯一可持续依赖的更新信任根。若私钥永久丢失，旧用户不能安全接收新信任根，只能手动安装新的引导版本。
- 更换、迁移、导出或恢复私钥属于单独的高风险发布操作；实现阶段到达该步骤时必须停下，由用户明确授权并亲自确认备份位置。
- 私钥生成后先完成“导出备份 → 从备份恢复到隔离钥匙串或测试环境 → 成功签名测试产物”的恢复演练，再把 `v0.0.3` 视为可发布。

## 版本与兼容性

- `MARKETING_VERSION` 对应用户看到的语义版本；首个引导版本为 `0.0.3`。
- `CURRENT_PROJECT_VERSION` 是 Sparkle 比较更新顺序的构建号，必须是严格递增的整数；`v0.0.3` 从当前构建号 2 递增。
- `v0.0.4` 是第一份完整端到端应用内升级验证目标，不允许复用 `v0.0.3` 的构建号。
- Git 标签、GitHub Release、DMG 文件名、更新说明和 appcast 中的展示版本必须一致。
- appcast 的更新比较值使用构建号，展示值使用语义版本，发布脚本验证两者不能颠倒或遗漏。
- appcast 明确声明最低系统版本为 macOS 15，并继续发布 Apple Silicon 与 Intel 均可运行的 Universal App。
- 第一版只发布完整 DMG，不生成或发布增量更新；以后启用 delta 前必须单独评估签名、回退和产物保留策略。
- P6 不提供降级、回滚到旧版本或跨稳定通道切换。

## 托管与发布顺序

### GitHub Release

- 更新包继续发布到 `ShunyangLiu/Lurume` 的 GitHub Releases。
- Release 先以草稿形式创建并上传 DMG；资产名称和下载 URL 必须可预测且与 appcast 一致。
- Release 转为公开后，发布脚本通过 HTTPS 验证 DMG 可下载、长度与准备阶段清单一致。
- P6 不使用 `.pkg` 安装器，不把额外脚本、文档或多个 App 放入更新归档。

### GitHub Pages

- GitHub Pages 保存稳定通道 appcast 和签名后的外部更新说明。
- 只有 GitHub Release 已公开且 DMG 下载验证通过后，才更新 Pages；禁止先让客户端看到尚不存在的资产。
- Pages 更新失败时保留已经公开的 Release，但客户端继续看到旧 appcast；脚本支持在不重建或覆盖 Release 的前提下安全重试 Pages 发布。
- appcast 更新必须原子化或以一次 Git 提交发布，不能暴露半写入 XML。
- 第一版不增加国内镜像。GitHub 暂时不可达时更新失败应可恢复，不影响本地阅读；若真实用户持续遇到访问问题，再单独讨论镜像和签名一致性。

## 单一更新说明来源

- 每个版本在仓库中保存一份中文 Markdown，例如 `release-notes/v0.0.4.md`。
- 同一文件同时作为 GitHub Release 正文和 Sparkle 外部更新说明来源，不能在网页上另写一份会漂移的内容。
- Sparkle 的 `releaseNotesLink` 指向 GitHub Pages 上由该 Markdown 原样生成并签名的静态文件，不直接指向可能被 GitHub 重排或插入页面元素的 Release 网页。
- 第一版更新说明只使用标题、段落、链接和列表，不嵌入远程图片、脚本、表单或跟踪资源。
- 文件至少包含版本号、发布日期、主要变化、修复和必要的兼容性说明。
- `prepare-release` 校验文件存在且标题版本与目标版本一致；`publish-release` 不接受临时输入的另一份正文。
- 发布后的历史 Markdown 保留在仓库中，不覆盖旧版本更新说明。

## 本地发布工具

P6 增加两个职责严格分开的本地命令。具体实现语言不是核心产品组件，可以在不改变以下边界的前提下选择最小可靠方案。

### `prepare-release`

该阶段只生成和验证本地产物，不改变 GitHub 或 GitHub Pages：

1. 接收明确的语义版本和构建号，并验证格式、递增关系及更新说明文件；
2. 验证 Git 工作区干净、当前提交已确定、依赖解析文件存在且 Sparkle 版本正确；
3. 使用锁定的 `Package.resolved` 运行完整自动化测试和 Release 构建，禁止在发布过程中自动升级或重新解析依赖；
4. 验证 App 为 Universal、部署目标为 macOS 15、沙盒 entitlement 和 Sparkle 配置完整；
5. 使用 macOS 系统工具生成保留 App bundle 结构和符号链接的 DMG；
6. 使用钥匙串中的 EdDSA 私钥签名更新归档，并生成签名 appcast 与更新说明；
7. 验证 DMG、appcast、更新说明签名、文件长度、下载 URL 模板和版本字段；
8. 验证第一版 appcast 不含 delta enclosure 或增量更新资产；
9. 输出只读发布清单，记录版本、构建号、Git SHA、Sparkle 版本、哈希、长度和产物路径。

准备阶段失败时不留下可被误发布的部分 appcast；临时目录与最终待发布目录分开，只有全部验证成功后才原子移动到最终目录。
该阶段不调用 GitHub API、不推送 Git、不上传文件，并应在依赖已缓存的前提下可以断网运行；若本机缺少锁定依赖，先退出并要求显式完成依赖获取，不能在发布构建中悄悄改写解析结果。

### `publish-release`

该阶段会改变公开状态，必须在执行前要求用户明确输入并确认目标版本：

1. 重新验证工作区、Git SHA、发布清单、签名和待发布文件未发生变化；
2. 验证同名标签、GitHub Release 和 Pages 版本尚不存在，禁止覆盖已有公开资产；
3. 将 `v<语义版本>` 标签明确绑定到发布清单记录的 Git SHA，再创建 GitHub Release 草稿并上传 DMG；GitHub Release 正文取自唯一 Markdown；
4. 将 Release 转为公开，验证匿名 HTTPS 下载、长度和文件哈希；
5. 最后发布 appcast 与更新说明到 GitHub Pages；
6. 再次读取公开 appcast，确认签名、版本和下载 URL 与本地发布清单一致；
7. 输出最终 Release、DMG、appcast 与更新说明链接。

脚本需要支持“Release 已成功但 Pages 失败”的安全重试，不得为了重试删除标签、覆盖 Release 或重新生成不同签名的同版本 DMG。P6 不自动撤回已经公开的版本；若发布内容错误，使用更高构建号发布修复版本。

## 保存、退出与失败回退

- Sparkle 请求退出并安装前，必须经过 Lurume 现有保存边界：刷新待保存页码、关闭或保存笔记草稿、完成文献库延迟写入。
- 现有高亮与笔记即时原子保存规则不因更新改变；P6 不把用户数据复制进更新目录。
- 更新检查、下载或验证失败时，当前 App bundle 和全部用户数据保持不变。
- 签名不匹配、appcast 签名无效、文件长度不符或版本倒退时必须拒绝安装，不能提供“仍然安装”绕过入口。
- 安装期间意外退出、磁盘空间不足或目标目录不可写时沿用 Sparkle 的原子安装与错误恢复，不自行实现文件替换。
- 新版本启动失败时 P6 不自动回滚；用户仍可从 GitHub Release 手动下载旧版本，但数据格式是否可向后兼容由对应功能版本决定。
- 后台自动检查不得因网络失败修改“自动检查更新”偏好，也不得在下一次启动进入错误循环。

## 隐私与本地优先

- 更新功能只访问固定 HTTPS appcast、签名更新说明和 GitHub Release 资产。
- 不向更新源发送文献库数量、论文标题、作者、文件名、路径、书签、页码、高亮、笔记、搜索词或翻译内容。
- 不启用 Sparkle 系统配置档案上报，也不添加自有分析 SDK。
- 自动检查权限提示和设置文案使用简体中文，说明其用途是获取 Lurume 版本更新。
- 用户关闭自动检查后，不保留自建定时器或绕过 Sparkle 偏好继续联网；手动“检查更新…”仍然可用。
- P6 不改变 PDF 文件只读访问、不写回原 PDF，也不改变现有本地 JSON 数据存储。

## 性能与观察方法

以当前已发布的 `v0.0.2` 和首个 Sparkle 构建使用同一台真实 Mac、同一启动模式和同一文献库进行对比，至少记录：

- `.app` 与 DMG 文件大小；
- 三次冷启动到主窗口可交互的中位数；
- 启动后 60 秒和 10 分钟的主进程空闲内存；
- 打开同一 PDF 后静置 5 分钟的主进程内存；
- 一次“无可用更新”检查完成后立即及 60 秒后的主进程和 Sparkle 辅助进程状态；
- 打开并关闭“发现更新”窗口前后的内存；
- 连续执行 20 次手动无更新检查后的响应、内存趋势和辅助进程残留。

P6 不在实测前虚构固定的包体或内存上限，但必须满足：启动和 PDF 阅读不等待网络；多次检查后的内存是有界并可回落的；无更新检查结束或更新窗口关闭后不存在持续运行的 Sparkle 辅助进程。若主进程出现持续增长、明显阅读卡顿或辅助进程无法退出，P6 不进入发布检查点。

## 键盘、中文与可访问性

- 应用菜单项命名为“检查更新…”，遵循 macOS 省略号与菜单排序习惯。
- 设置中的自动检查开关提供完整简体中文标签、说明和辅助功能值。
- Sparkle 标准权限、无更新、发现更新、下载、验证、安装和错误界面必须在当前系统语言下实际检查简体中文显示。
- 不能把英文 Sparkle 专有名词直接暴露给普通用户；诊断日志可以保留框架和错误代码。
- 更新状态不能只依赖颜色表达；按钮、进度和错误由 Sparkle 标准辅助功能语义暴露。
- “检查更新…”不设置会与 PDF 搜索、翻译、高亮、元数据编辑或系统菜单冲突的自定义快捷键。
- 如果固定版本的 Sparkle 缺少关键简体中文本地化，先停止并讨论；P6 不在未确认的情况下改成自制更新界面。

## 与现有阶段和文档的兼容裁决

- P0 与早期 README 的“无运行时第三方依赖”已由 P6 产品决定调整；历史计划保持原样，README 当前承诺明确 Sparkle 是唯一基础设施例外。
- P0–P5 的 PDF 阅读、翻译、高亮、笔记、导航、元数据和文献集能力不因 P6 更换核心组件。
- P5 的“不联网抓取书目元数据”继续有效；P6 的网络访问只用于应用更新，不能顺带扩展 DOI、arXiv、期刊或引用查询。
- P6 不修改文献库 schema 4 或高亮 schema 2，也不新增用户数据迁移。
- 设置窗口仍保持统一的“通用 / 翻译”结构；更新选项进入“通用”，不在阅读区或翻译检查器增加入口。
- README 已明确取消“安装包必须为个位数 MB”的硬指标；P6 完成后补充应用内更新和手动检查说明，但不删除未公证应用的首次安装提示。

- DOI、arXiv、Crossref、引用格式或其他文献联网能力

## 四个实现检查点

检查点一的实测记录见 [`P6-checkpoint1.md`](P6-checkpoint1.md)。该记录只补充实现证据，不改变以下已冻结范围。

### 检查点一：最小依赖、沙盒与可行性

- 固定经过核验的 Sparkle 稳定版本，通过 XcodeGen/Swift Package Manager 加入工程。
- 只接入标准更新控制器、沙盒 Installer/Downloader 服务和必需 entitlement，不增加完整产品界面。
- 生成真实 Release App 和 DMG，记录引入前后的包体、启动和空闲内存。
- 使用一次性测试密钥和隔离 feed 验证当前临时签名、无 Developer ID、公证缺失和 App Sandbox 组合能够从旧构建安全安装到高构建号测试版本；该密钥不进入正式 App、Pages 或 Release。
- 如果临时签名导致 Sparkle 无法可靠安装、内嵌 XPC 无法验证或必须降低签名安全，立即停止并向用户报告；不能把产品降级成不安全的文件替换器，也不能擅自改成仅打开下载网页。

### 检查点二：密钥、签名更新源与拒绝路径

- 在用户明确授权下生成 EdDSA 密钥，完成离线备份和恢复演练。
- 配置公钥、HTTPS feed、解压前验证和签名 feed。
- 建立本地签名 appcast、更新说明和 DMG 测试样本。
- 验证有效更新可识别，篡改 DMG、appcast、更新说明、长度、版本或下载地址均被拒绝。
- 完成后暂停，由用户确认安全链路和私钥备份状态再进入界面集成。

### 检查点三：菜单、设置、许可与退出保存

- 加入“检查更新…”、自动检查开关和第二次启动许可流程。
- 检查全部 Sparkle 标准界面的简体中文与辅助功能。
- 验证后台失败低干扰、手动失败可理解、自动检查关闭后不再联网。
- 验证安装重启前页码、文献库和笔记草稿保存，更新后阅读状态完整恢复。
- 运行现有全部自动化测试和新增加的更新控制器测试。

### 检查点四：发布脚本与 `v0.0.3 → v0.0.4`

- 完成 `prepare-release` 与 `publish-release`，包含干运行、失败注入和安全重试验证。
- 使用 `release-notes/v0.0.3.md` 准备引导版本，并由用户手动安装。
- 使用 `release-notes/v0.0.4.md` 发布第一份应用内升级验证版本。
- 从安装在可写位置的真实 `v0.0.3` 检查、下载、验证、安装并重启到 `v0.0.4`。
- 核对公开 Release、Pages、appcast、签名、版本、下载长度和中文更新说明完全一致。
- 完成性能记录、README 发布说明和最终人工验收后，P6 才能标记完成。

每个检查点单独提交并运行全量测试与 Release 构建。到达密钥生成、首次公开 Release 或 Pages 发布等会改变外部状态的步骤时必须停下取得用户授权。若实现需要替换 Sparkle 标准更新器、现有 App Sandbox、XcodeGen 工程源或本计划中的其他核心组件，必须先停止并取得用户确认，不能先改代码再回写计划。

## 验收标准

P6 第一版需要同时满足以下条件：

1. `v0.0.3` 包含固定版本的官方 Sparkle 2，现有 P0–P5 功能和沙盒 PDF 只读访问无回归。
2. Lurume 主进程没有通用 network client entitlement；更新检查与下载只通过计划中的 Sparkle 专用服务完成。
3. 首次启动不显示许可，第二次启动显示简体中文自动检查许可；拒绝后不自动联网，手动检查仍可用。
4. 应用菜单“检查更新…”和设置中的自动检查开关状态准确、可访问且不保存重复偏好。
5. 允许自动检查后按 Sparkle 调度约每 24 小时检查；没有更新和后台网络失败不会干扰阅读。
6. 有稳定新版本时显示中文更新说明；只有用户确认后才下载、安装和重启，不静默安装。
7. 有效签名的 DMG、appcast 和更新说明可以完成更新；任一内容被篡改、长度不符或版本倒退都被拒绝。
8. `SUPublicEDKey`、解压前验证、签名 feed、禁止失败到期回退、禁用自动安装与系统配置档案、Installer Service 和 Downloader Service 配置与固定 Sparkle 版本官方文档一致。
9. 私钥不出现在仓库、构建产物、脚本参数、日志或 GitHub；离线备份与恢复签名演练完成。
10. `prepare-release` 在本地完成测试、Release 构建、Universal/部署目标/entitlement 校验、DMG、签名、appcast 和发布清单，且不改变远端状态。
11. `publish-release` 只有在明确版本确认后才发布；Release 下载验证成功后才更新 Pages，任何中途失败都不会向客户端暴露坏版本。
12. Git 标签、语义版本、构建号、DMG、唯一 Markdown、GitHub Release 和 appcast 内容一致；同版本不能覆盖发布。
13. 从真实 `v0.0.3` 可以通过稳定更新链路升级到 `v0.0.4` 并重新启动，当前文献库、论文、页码、高亮和笔记完整保留。
14. 网络不可达、GitHub 限流、无更新、目标不可写、DMG 下载中断和磁盘空间不足均不损坏当前 App 或用户数据。
15. 从不可更新位置手动检查时提供准确移动提示；后台检查不会因此持续弹窗。
16. 更新前退出保存边界覆盖页码、文献库延迟保存和打开的笔记草稿；安装重启不丢失最后编辑。
17. App 和 DMG 体积、冷启动和内存变化已记录；启动与 PDF 阅读不等待网络，多次检查无持续内存增长或辅助进程残留。
18. Sparkle 权限、无更新、发现更新、错误和安装流程均完成简体中文与 VoiceOver/键盘检查。
19. 现有 P0–P5 自动化测试全部继续通过，并新增覆盖更新菜单状态、设置绑定、版本映射、退出保存边界和脚本输入验证的测试。
20. README 保留未公证首次安装提示，同时补充应用内更新说明、Sparkle 依赖例外和最新性能记录链接。

## 验收样本与故障矩阵

P6 至少准备以下隔离样本：

- 一个当前版本与 feed 相同的“无更新”样本；
- 一个低构建号 App 到高构建号 DMG 的有效签名更新样本；
- 被修改一个字节的 DMG、appcast 和更新说明各一份；
- 正确签名但版本倒退、最低系统版本不兼容、长度错误和下载 URL 不存在的 appcast 项；
- 网络断开、DNS 失败、GitHub 限流和下载中断场景；
- 从可写应用目录、只读 DMG 和不可写位置启动的场景；
- 包含待保存页码、文献库修改和未关闭笔记草稿的更新重启场景；
- Apple Silicon 真实安装升级，以及对 Universal 二进制 Intel slice 的构建与静态校验；条件允许时再做 Intel 真机升级。

更新测试使用隔离产物、隔离 feed 和已备份的测试数据，不覆盖用户正在日常使用的 Lurume。首次操作真实稳定 feed、GitHub Release、GitHub Pages 或本机更新私钥前必须再次确认精确目标。

## 文档自审记录

本计划在进入实现前按六个方面完成自审：

1. **安全与信任根**：确认 DMG、appcast 和更新说明均需签名，正式私钥只在检查点二经用户授权后生成；检查点一改用一次性测试密钥，避免可行性尚未证明就创建生产信任根。官方复核还发现签名 feed 默认具有失败到期回退，因此计划明确将该间隔设为 `0`，没有 Developer ID 时不允许绕过信任根。
2. **发布失败回退**：确认发布顺序固定为“Release 草稿与资产 → Release 公开并验证 → Pages appcast”，Pages 失败时客户端继续读取旧 feed；同版本资产不覆盖，错误版本只通过更高构建号修复。
3. **隐私与沙盒**：确认主进程不增加通用网络 entitlement，不上传系统配置档案或任何文献数据；专用 Downloader XPC 的边界和官方未沙盒化现状已经显式记录为实现审计项。官方复核发现默认许可界面可能允许用户选择后台下载，因此计划明确禁用自动更新选项，保证每次安装都需确认。
4. **轻量化与内存**：取消未经实测的 DMG 硬门槛，保留 App/DMG、启动、空闲内存、重复检查和辅助进程退出测量；持续增长或阅读卡顿会阻止进入发布检查点。
5. **旧版本引导与可行性**：确认 `v0.0.2` 无法自更新，`v0.0.3` 必须手动安装，`v0.0.4` 才验证完整链路；无 Developer ID 的临时签名组合被列为检查点一的阻塞性实测，而非文档中的既成事实。
6. **跨文档与发布一致性**：确认 README 已明确 Sparkle 例外和新的轻量化承诺；唯一 Markdown 经签名后发布到 Pages，Git 标签明确绑定准备阶段 Git SHA，版本、构建号、Release、DMG 和 appcast 均有一致性校验。自审期间重新核对官方发布页，将过时的 `2.9.4` 基线修正为带有后续安全修复的 `2.9.6`。

自审没有发现需要扩大 P6 产品范围的阻塞项。实现阶段最大的未知仍是“临时签名 + App Sandbox + Sparkle XPC”能否可靠完成真实安装，因此检查点一必须先证明该组合；若失败，按计划停止讨论，不自动降低安全标准或改写 P6 目标。

## P6 完成之后

P6 完成后先用至少两个真实稳定版本观察 GitHub 在中国大陆的检查和下载可用性、更新提示频率、安装成功率以及内存变化。只有持续出现访问问题时再讨论国内镜像；只有完整更新包的下载成本形成实际问题时再讨论 delta；只有本地两阶段脚本稳定后再评估是否把非签名步骤迁移到 CI。书目元数据、BibTeX/RIS、标签和嵌套文献集继续作为 P6 之后的独立产品方向，不与更新基础设施捆绑。
